Installing someone else's dotfiles is the quickest way to a good-looking Linux desktop, and the quickest way to lose your own setup. This guide explains what an install actually changes, how to see the plan before anything happens, and how to get back to where you were. It uses the installers generated by 0xTsoa as the example, but every step also applies when you install by hand.

## What a dotfiles install actually changes

"Dotfiles" sounds like a few hidden files, but an install usually does up to four different kinds of thing, and each one is undone differently.

1. **Files in your home folder.** Config folders copied into `~/.config`, a cloned repository, a line added to `~/.bashrc`. This is the part a backup can restore.
2. **Packages.** <RegistryStat kind="packages" /> of the <RegistryStat kind="installers" /> installs in the registry add packages from your distro, and <RegistryStat kind="aur" /> use the Arch User Repository. Packages stay installed after you restore your files.
3. **The project's own installer.** <RegistryStat kind="upstream-installer" /> installs hand over to a script written by the project itself, such as `./setup.sh`. That script decides what it touches, which can include your shell, your login screen and your bootloader.
4. **Changes outside your home folder.** <RegistryStat kind="sudo" /> installs use sudo for more than packages, for example to copy a theme into `/usr/share`.

## Before you start: choose your safety net

Pick at least one of these. The more an install changes, the stronger the net you want.

**A second user account.** Create a user just for trying setups, log in to it from your login screen, and install there. Your own home folder is never touched. Packages are still installed for the whole system.

```bash
sudo useradd -m tryout
sudo passwd tryout
```

**A virtual machine.** The safest option for a complete desktop that runs its own installer. Some projects offer a live ISO you can boot in a VM before installing; ML4W does. Wayland compositors with animations, like Hyprland, usually need 3D acceleration enabled in the VM.

**A system snapshot.** On Btrfs, Snapper or Timeshift can take a snapshot of the system before you install, and roll back packages and system files afterwards. Both normally leave your home folder out: Timeshift excludes home folders by default, and Snapper's root configuration does not include a separate home subvolume. So a snapshot covers what a file backup does not, and the other way round.

```bash
sudo timeshift --create --comments "before dotfiles"
# or, with Snapper:
sudo snapper -c root create --description "before dotfiles"
```

**A copy of your config folders.** The minimum, and enough for setups that only copy files. Copy the folders the setup writes to, or all of `~/.config`:

```bash
cp -a ~/.config ~/config-backup-$(date +%F)
```

## Read the plan before anything happens

Download the installer instead of piping it into a shell. A pipe runs code you have not read, and runs a truncated script if the download is cut off. Each config page shows the exact command:

```bash
curl -fsSLo install.sh https://www.0xtsoa.dev/configs/end-4/dots-hyprland/install.sh
less install.sh
```

If you have the GitHub CLI, you can also check that the file is the one built by 0xTsoa's own workflow, not a modified copy:

```bash
gh attestation verify install.sh --repo nyharena25/0xTsoa --signer-workflow nyharena25/0xTsoa/.github/workflows/attest-installers.yml
```

Then ask for the plan. `--dry-run` writes nothing, installs nothing and never calls sudo:

```bash
bash install.sh --dry-run
```

Every line of the plan starts with a label:

| Label | Meaning |
| --- | --- |
| `[download]` | The project's source, fetched into a cache folder (`~/.cache/0xtsoa`). |
| `[new]` | A file or folder that does not exist yet; it will be created. |
| `[same]` | Already identical; skipped. |
| `[update]` | An existing clone of the same repository; backed up, then updated. |
| `[append]` | A line added to a file, such as `~/.bashrc`; the file is backed up first. |
| `[conflict]` | Something different is already there; you are asked before it is replaced. |
| `[package]` | A package install, with your package manager and sudo. |
| `[upstream]` | The project's own installer, with the folders backed up before it runs. |
| `[system]` | A sudo change outside your home folder, not undone by a rollback. |
| `[run]` | A command run as written, such as reloading your compositor or changing a setting. |
| `[manual]` | A step you do yourself. |

The summary at the end counts them and says what a rollback will and will not undo. If the plan shows something you do not expect, stop there: nothing has changed yet.

## Install, and keep your own files

Run the script as your normal user, without sudo. It asks for sudo itself at the steps that need it, and refuses to run as root, because files written by root in your home folder can break your desktop.

```bash
bash install.sh
```

It shows the plan again and asks before doing anything. Then, before each change, it copies the file or folder it is about to change into a backup and checks the copy; if the backup fails, it stops before making the change. When a file already exists and differs, it asks you to keep yours (the default), replace it, or see the difference first.

Two options change that behaviour. `--yes` never asks, and still keeps your conflicting files. `--force` replaces them, after backing each one up. Use `--force` only when you have read the conflicts in the plan.

## Undo it with `--rollback`

To go back, run the same script with `--rollback`:

```bash
bash install.sh --rollback
```

It lists what it will do and asks first:

- files and folders that existed before are restored from the backup;
- files and folders the install created are moved aside, not deleted;
- packages and sudo changes are listed as kept, so you know what is left to remove by hand.

Backups live in `~/.local/state/0xtsoa/backups/` (one folder per setup, then one per install, named by date), with a copy of the script that made them. A rollback can itself be undone: whatever was in place before it is kept in that backup's `undone` folder. Running `--rollback` again goes back one more install.

What a rollback does not undo:

- **Packages.** Remove them with your package manager, for example `sudo pacman -Rns`, `sudo apt remove` or `sudo dnf remove`, followed by the package names the rollback listed.
- **Sudo changes and settings commands**, such as files copied into `/usr/share` or a `gsettings set`. The plan marks them as `[system]` and `[run]`. A system snapshot taken before the install is the easy way back.
- **Whatever a project's own installer writes outside the folders listed in the plan.** For those setups, the backup covers the usual config folders (`~/.config/hypr`, `~/.config/waybar`, `~/.zshrc` and similar), not everything the script can reach. Read the project's README for what else it changes, and prefer a second account or a VM.

## Installing by hand instead

You do not need an installer at all. The safest manual install takes one part at a time:

1. Read the project's README and note every folder it asks you to copy.
2. Back up those folders.
3. Copy one folder, such as the bar config, restart that program, and check that it works.
4. Move on to the next part only once the previous one does.

If you plan to keep and change the setup, put it under version control from day one. A dotfiles manager keeps your files in a Git repository and links or copies them into place, so going back is a `git checkout` away. GNU Stow links folders into place, [chezmoi](/configs/twpayne/chezmoi/) manages templates and differences between machines, [yadm](/configs/yadm-dev/yadm/) wraps Git around your home folder, and [Dotbot](/configs/anishathalye/dotbot/) and [Dotter](/configs/supercuber/dotter/) install from a config file.

## A short checklist

- Read what the setup changes: the "At a glance" panel on its page, or its README.
- Pick a safety net: another account, a VM, a snapshot, or at least a copy of `~/.config`.
- Download the script, read it, and run `--dry-run`.
- Install as your normal user, and keep your files when asked unless you mean to replace them.
- Keep the backup until you are sure you like the new setup.
